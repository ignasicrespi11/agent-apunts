# Architecture

Status: accepted 2026-09-29 (Opus). Each decision lists **why** and the **rejected alternative**, so it can be defended in interviews.

## Product idea
Users upload their course material (slides, exams). The system processes it once and then answers questions
**only from that material**, citing the exact slide, not from the model's general knowledge or the internet.

## Data flow

```
INGESTION (once per file, incremental)
 apunts/ (inbox) + testing/apunts_testing/ (manually labelled set); originals never modified
   1. REGISTER   file hash = document ID; skip if already processed           → data/manifest.sqlite
   1b. DETECT    metadata (subject, doc_type, professor, year) from folder hint > title slides + filename (LLM),
                 with confidence; low confidence → ask the user to confirm            (D18, from week 4)
   2. EXTRACT    per slide: title, text, language, PNG thumbnail, "mostly image" flag
                                                                               → data/processed/<user_id>/<doc_id>.json
   3. CLEAN      remove lines repeated on most pages of a document + page numbers, listed for audit (D27)
   4. CHUNK      size decides: page ≤ 450 words = 1 chunk, longer pages split by paragraphs (D26); contextual header
   5. INDEX      embed (Ollama bge-m3, D28) + upsert to Qdrant (vector + metadata payload + user_id), idempotent IDs (D29)

QUERY (never touches the PDFs)
 question + user_id (+ subject) ─► embed (same model) ─► Qdrant search WITH filter
   ─► relevance threshold (abstain if nothing relevant) ─► prompt with numbered sources
   ─► LLM ─► answer with citations (subject, document, slide) + user_id ─► log
```

Phase 2 wraps the query side in an agent: the LLM chooses tools (`search_notes`, `list_subjects`, `get_document`),
adds an upload UI that feeds the same pipeline, and an optional vision enrichment step (D14).

## Decisions

| # | Decision | Why | Rejected |
|---|---|---|---|
| D1 | Hand-written RAG pipeline | ~300 lines, every step explainable; easier to debug | LangChain / LlamaIndex: hides internals, APIs change often |
| D2 | Qdrant in Docker | Filtering inside the query; multi-tenant pattern (payload index on `user_id`); hybrid search | Chroma (weaker multi-tenancy), pgvector (more SQL work now) |
| D3 | Local multilingual embeddings (bge-m3) | Slides mix Catalan/Spanish/English; cross-lingual retrieval; free and private | English-only models; paid embedding APIs |
| D4 | `LLMClient` interface: **Ollama (local) first**, Claude API later via config | Free while developing; switching is a config line; the eval measures the quality gain | Coupling code to one provider |
| D5 | Metadata: university/degree from user profile in config; subject + doc_type from path `<root>/<subject>/<doc_type>/` (until D18, then an optional hint); professor (optional) + year taken from `sources.yaml`; one Pydantic model (D21) | Simple for the user; upload form and auto-detection fill the same model | Metadata in code; deep folder trees |
| D6 | Deterministic chunk IDs | Re-ingest is idempotent (no duplicates) | Random UUIDs |
| D7 | `user_id` passed explicitly everywhere | Multi-user later only changes where the value comes from | Global constant |
| D8 | Evaluation from week 4 (hit@k, MRR, faithfulness, abstention) | Proves improvements with numbers | "Looks good" manual testing |
| D9 | CLI first, then FastAPI + Streamlit | Fast to develop and evaluate; demo UI later | Building a web UI first |
| D10 | uv + devcontainer + docker-compose + pytest | Identical environment on Arch and Windows | Manual venvs per machine |
| D11 | Staged pipeline with persisted intermediate outputs | Inspectable (open the JSON); re-run one stage only (new chunking or embedding model without re-reading PDFs) | One script PDF → Qdrant |
| D12 | Document ID = content hash + manifest of stage status | Incremental, detects duplicates, survives renames | Filename as ID |
| D13 | **Layout-aware chunking** (revised after corpus analysis): slide-like page (landscape, little text) → 1 page = 1 chunk; document page (portrait A4, dense text) → split by headings/paragraphs into ~300–500-word chunks. Page number kept on every chunk; contextual header `[subject · document · title]` on all. Detected automatically per page | Real corpus has both kinds (slides ~330 chars/page vs A4 docs ~4,000); one vector per dense page averages several topics and hurts retrieval; future uploads are heterogeneous, so the chunker must adapt to the input | One rule for all (1 page = 1 chunk, or fixed 500-token windows everywhere) |
| D14 | Images: phase 1 text + thumbnail + "mostly image" flag; phase 2 optional vision-model description, config-toggled and measured | Diagrams hold knowledge, but vision is slow/costly: measure first | OCR only (reads words, not diagrams); ignoring images |
| D15 | PyMuPDF for extraction (AGPL, fine for open source) | Fast, per-page text, renders thumbnails for the demo | pypdf (weaker); Docling kept as fallback if layout order is bad |
| D16 | Language detected per slide, stored as metadata | Enables per-language analysis; verifies cross-lingual retrieval | Assuming one language per document |
| D17 | Course material never leaves the machine: `.gitignore` + pre-commit hook block PDFs/Office files, `apunts/`, `testing/`, `data/` | Professors' slides and exams are copyrighted; the repo is public | Relying on `.gitignore` alone (`git add -f` bypasses it) |
| D18 | Automatic metadata detection: folder name (if any) wins; otherwise LLM reads title slides + filename and returns fields + confidence; low confidence → user confirms. Phase 2: folder watcher + upload UI use the same detector. Manually organised subjects are the ground truth to measure its accuracy | Users just drop PDFs; accuracy is measurable (e.g. "subject correct in 94% of documents"); built after the pipeline works so failures are attributable | Mandatory manual folders forever (bad UX); auto-detection from day 1 (no LLM yet, no way to measure it) |
| D19 | Near-duplicate handling (phase 2): exact duplicates skipped by hash (D12); near-duplicates (translations, statement vs solutions) detected at ingestion by document-level similarity and given a shared `group_id` in the payload; at query time results are collapsed by `group_id` (Qdrant grouping) so top-k shows distinct documents | Users will always upload overlapping material; keeping all versions preserves cross-lingual value while avoiding a top-5 full of the same exam | Deleting near-duplicates (loses languages/solutions); ignoring them (redundant results) |
| D20 | Configuration: `config/settings.yaml` + `config/sources.yaml` (shared, committed) and `.env` (per machine: paths, URLs, secrets), merged by a **hand-written loader** (~100 lines: PyYAML + python-dotenv + Pydantic) into one frozen `Settings` object. Only the env vars listed in the loader are read; priority real env > `.env` > default; relative paths resolve against the project root; unknown YAML keys are errors. The rest of the code only receives `Settings` (and `user_id` as a parameter) | Every value's origin is visible and defensible; a typo fails at startup, not mid-ingest. Scaling path: deployment → switch the loader to `pydantic-settings` (servers are configured by env vars); multi-user → user profile + subjects move from YAML to a database. Both changes stay inside `config.py` | `pydantic-settings` now (source priority hidden in the library; any field silently overridable by a forgotten env var); reading `os.environ` / YAML wherever needed (no single place to change) |
| D21 | `DocumentMetadata` describes *what* a document is (university, degree, subject, doc_type, `taken_in`, optional `academic_year`, optional `professor`); ownership (`user_id`) is stored next to it (manifest, chunks), not inside. Two years: `taken_in` (when the user took the subject, per subject in `sources.yaml`) vs `academic_year` (the document's own year, from filename now, D18 later). Model is frozen and rejects unknown fields | The same PDF can belong to several users while its subject stays the same; corpus has 2022-23 exams in a subject taken in 2025-26, so one year field would lose information | `user_id` inside the metadata; a single year field defaulting to the subject's year |
| D22 | Manifest = one SQLite file (`data/manifest.sqlite`, stdlib `sqlite3`, schema version in `PRAGMA user_version`): `documents` (PK `user_id, doc_id`; `source` + path relative to the source root; metadata as JSON) and `stages` (per document: stage, producer version e.g. `pymupdf-1`, output path). A stage is redone when its producer version changes or its output file is gone. Moves keep the ID and completed stages; exact duplicates and vanished content are reported, never silently deleted | A file: nothing to install; transactional (crash-safe); readable with any SQLite viewer; relative paths keep it valid if `data/` is copied to another machine; versioned stages make "re-extract everything after improving the extractor" one number bump | JSON manifest file (no transactions, rewrite on every change); Qdrant payload as the only record (can't track stages that happen before indexing); absolute paths (break across machines) |
| D23 | Loaders: a `Loader` Protocol (`name`, `version`, `extensions`, `load() -> list[RawPage]`) and an explicit registry (extension → loader, one line per format). Loaders only read their format; language detection, the mostly-image flag, cleaning and chunking run afterwards, the same for every format | Adding DOCX/PPTX = one module + one line, and every format gets identical downstream processing | Abstract base class hierarchy (more ceremony); plugin auto-discovery (implicit: you can't see what's supported); per-format logic for language/cleaning |
| D24 | Extraction output: `data/processed/<user_id>/<doc_id>.json` + `data/thumbnails/<user_id>/<doc_id>/p0001.png`, written atomically (temp file + rename). Per page: number, size (points), title guess (largest text with letters/digits in the top 30% of the visible page, if its font is ≥15% larger than body text; tuned on the real corpus: precision over coverage, a wrong title pollutes every chunk header), NFC-normalised text in reading order (`sort=True`), char count, language, image count, mostly-image flag, thumbnail. Layout (slide vs document, D13) is decided in the chunking stage from these facts | Per-user folders make deleting a user's data trivial; atomic writes mean "stage done" always points to a complete file; storing facts (size, char count) instead of decisions lets chunking rules change without re-extracting | Writing straight to the final file; classifying layout during extraction |
| D25 | Language detection: `py3langid` restricted to `languages` from settings (ca/es/en), per page; `None` below `language_min_chars` letters or `language_min_confidence` | ~5 MB, offline, deterministic; restricting to 3 languages makes Catalan vs Spanish reliable on short slides; "unknown" is better than a wrong label | `lingua` (170 MB wheel), `langdetect` (non-deterministic), fastText detectors (download models at runtime) |
| D26 | **Chunking: size decides** (refines D13). A page with ≤ `max_words` (450) words is one chunk; a longer page is cut at paragraph boundaries (blank lines), then line boundaries, into chunks of ~`target_words` (350), never above `max_words`. Every chunk keeps its page number. Contextual header `subject name · document · title (or "p. N")` is prepended to the text **for embedding only**; payload stores text and header separately | One rule covers both page kinds found in the corpus (slides ~400 chars → whole page; A4 exams ~3,000 chars → split) and the odd cases (dense slide, near-empty A4); the header tells the embedding *where* the text comes from, which short slide text lacks | Shape decides (landscape = 1 chunk): a dense slide becomes one oversized, multi-topic vector; fixed token windows: cut slides in half |
| D27 | **Cleaning** (stage 3, run inside the chunk stage): per document, remove short lines (≤ 100 chars, containing a letter) that appear **identically** (case/spacing ignored) on ≥ 50% of pages (and ≥ 3 pages); remove a number-only line only if it is the first or last line of the page and equals the page number (or page − 1/2, unnumbered covers). Every removed line is listed in the chunk output, per document. Tests found two traps that shaped this: masking digits would delete "Exercici 1/2/3…" headings, and repeated numbers are exam-table data | Repeated footers/course names make every chunk of a document look alike to the embedding model; auditable removal lets us check nothing real (a formula) was deleted | No cleaning (noise in every vector); global stop-lines across documents (a phrase common to one subject's decks would vanish everywhere); a separate stage file (one more JSON with no other use) |
| D28 | **Embeddings via Ollama** (`bge-m3`, 1024 dims) behind an `Embedder` protocol (like `LLMClient`), batched calls to `/api/embed`. Model name + dimension are stored in the Qdrant collection metadata and checked before indexing or searching | No PyTorch in the project (GBs, CUDA vs CPU builds per machine); Ollama already runs the LLM and uses the GPU where there is one; the protocol keeps the provider swappable and lets tests use a fake embedder | sentence-transformers (heavy, fragile install on 3 machines); fastembed (light, but no bge-m3: would change D3) |
| D29 | **Pages and chunk identity, v1**: pages with < `min_words` (5) words produce no chunk (image-only/blank: D14 later); no title inheritance and no merging of consecutive slides (one chunk ↔ one exact page citation). Chunk/point ID = UUIDv5 of `user_id + doc_id + chunk index + text` (doc_id, not path, so moving a file keeps IDs). Re-indexing a document deletes its points that are no longer produced | Exact citations; no wrong inherited titles; the eval (week 4) decides whether merging/inheritance pay off. Content-derived IDs make re-ingest idempotent (same point count after two runs) | Inheriting the previous title (can be wrong across sections); path in the ID (a rename would duplicate every point) |
| D30 | **Measure hidden image content before building OCR/vision** (step 1 of D14): the PDF loader records `image_coverage` per page (share of the page covered by images, grid-sampled so overlaps count once); `agent-apunts images` reports per subject the image-only pages (not indexed) and the text + large-image pages (≥ 25%: indexed but incomplete, e.g. code screenshots in Disseny de Software). Next steps: golden questions about code examples (week 4) give the retrieval gap in numbers; then an optional local OCR stage (Tesseract, free) is built and measured against them | Raised by Ignasi: pattern/code examples are screenshots. Counting first tells whether it is 30 pages or 300, and the eval turns "OCR helps" into a number for the CV | Building OCR straight away (cost and complexity without knowing the gain); paid vision APIs (project rule: free, local tools) |
| D31 | *(proposed 2026-10-08, pending Ignasi's OK)* **`LLMClient` protocol** (`complete(system, user) -> LLMResponse`) with an **Ollama** implementation (`/api/chat`, non-streaming, `temperature: 0`, `num_ctx: 8192`), model from settings. No paid API is implemented (project rule): the Claude client stays on the roadmap behind the same protocol | Same pattern as `Embedder` (D28): tests use a fake, swapping provider is one class. Temperature 0 makes eval runs repeatable; Ollama's default context (2–4k tokens) is too small for 5 sources × ~450 words + instructions | Calling Ollama directly from the RAG code (untestable, provider lock-in); streaming (adds complexity, not needed for CLI/eval) |
| D32 | *(proposed)* **Grounded answering (`ask`)**: retrieve top-k (5) with the user/subject filter; **abstain without calling the LLM** if the best score < `retrieval.min_score` (provisional 0.45, calibrated by `eval --sweep`); otherwise send numbered sources `[n] subject · document · p. N` + text, with rules: use only the sources, cite `[n]` after each claim, answer in the question's language, reply exactly `NOT_FOUND` if the sources don't answer. Citations are parsed and mapped back to (document, page); invalid numbers are dropped; an answer with no valid citation is flagged `uncited` | Two abstention gates: a cheap numeric one (no LLM time wasted on unrelated questions) and the model's own judgement. Mapping `[n]` back to pages gives exact, checkable citations (the demo's core promise) | Free-form "answer using this context" prompts (no way to verify grounding); letting the LLM answer from its own knowledge when retrieval is weak |
| D33 | *(proposed)* **Query log**: one JSON line per `ask` in `logs/queries.jsonl` (gitignored): timestamp, `user_id`, question, filters, retrieved chunk IDs + scores, answer, citations, abstention reason, model, latency | CLAUDE.md requires `user_id` on every log entry; JSONL is append-only, greppable and loads straight into pandas for later analysis (faithfulness eval, phase 2) | A database table (overkill now); no log (no evidence for evaluation or debugging) |
| D34 | *(proposed)* **Retrieval eval harness**: golden set in `eval/golden.yaml` (Ignasi's own questions + expected `rel_path` and optional pages; no course text, so it can be committed). `agent-apunts eval` reports hit@k, MRR, per language and subject, plus abstention quality on unanswerable questions; `--sweep` tries `min_score` thresholds to calibrate D32. Results saved to `data/eval/` | Measures retrieval without the LLM (fast, deterministic, free), so every change (cleaning, chunking, OCR D30, hybrid search) gets a before/after number for the CV | Judging answers by eye; LLM-as-judge first (slower, needs a judge model; planned for faithfulness in phase 2) |
| D35 | *(proposed)* **Prune orphaned documents**: after `register`, a document whose recorded file is gone or now has different content (re-hashed) has no copy left; `prune` deletes its Qdrant points first, then its JSON, chunks, thumbnails and manifest row. `ingest` runs it automatically; `prune --dry-run` lists without deleting. PDFs are never touched | Found in self-review: a professor's updated PDF (same name, new content = new doc_id) left the old version searchable next to the new one, and deleted PDFs stayed citable. Only derived, rebuildable data is deleted; Qdrant goes first so a failure leaves nothing half-deleted | Keeping orphans (stale and duplicate citations); asking for confirmation on every run (the deleted data is all derived) |

## Grounding ("answer only from the notes")
Cannot be guaranteed 100%, but it is controlled and measured:
system prompt restricts to the retrieved sources · mandatory citations · relevance threshold → "not found in your notes" ·
faithfulness eval (LLM judge) in the golden set.

## Known risks (verify AI output here)
- Filter applied after retrieval instead of in the Qdrant call → check `retrieval.py`.
- Outdated Qdrant client API → check the docs for the installed version.
- Jumbled slide text order → compare processed JSON vs slide with `inspect <file> --page N`.
- Wrong title guess (decorative big text, image titles, bold-only headings) → `inspect` table, title column.
- Wrong language on short or mixed pages → `inspect` lang column; tune `language_min_*` in settings.
- Boilerplate removal deleting real repeated content (formulas) → compare char counts before/after.
- Image-only or protected PDFs silently empty → ingest report lists slides with no text.
- Duplicates on re-ingest → point count must stay the same after running ingest twice.

## Hardware notes
- Windows PC: 16 GB RAM + GTX 1080 (8 GB VRAM) → 7–8B local models at usable speed.
- MateBook 14 (Omarchy): CPU only → embeddings fine (one-off), local LLM limited to small models or slow.
- Ollama runs natively on the host, not inside the devcontainer (GPU passthrough on Windows is fragile).

## Out of scope (roadmap)
Authentication, billing/quotas, distributed deployment.
